## 1. 本輪做了什麼

### 1.1 tw-hold：長波段頁排序加「上榜天數」
`app/streamlit_app.py`：`SORT_KEYS["swing"]` 加 `"上榜天數": "streak_days"`，
新增 `SORT_ASC = {"streak_days"}`（只有它由小到大，其他排序仍由大到小）。
`streak_days` 由 `build_lists.py` 注入（連續入選天數，掉出池再回來會重算為 1），
舊資料沒有這個欄位時排最後。預設排序仍是市值。

### 1.2 tw-swing：publish_bundle 改成「接在 daily 後面」（重點）
**問題（用最近 10 次實測）**：tw-hold 的新資料多半在台股開盤（09:00）後才更新。
上游 data_pack.zip 台灣 05:08 就好了，但 tw-swing `publish_bundle.yml` 的單一 cron
（UTC 22:00＝台灣 06:00）被 GitHub 排程延遲約 3 小時，實際 09:02–09:16 才跑，
tw-hold 重算約 09:20 才完成。晚上 22:00 那輪「備援」只是用前一天早上發佈的 bundle
重跑，沒有新資料——所以開盤前看到的是**前一個交易日**的資料。

**改法（commit `855219b`，只改 publish_bundle.yml，daily.yml 一個字元沒動——它在 G-5 時鐘上）**：
- `on:` 加 `workflow_run`（聽「每日掃描與候選清單」completed、branch master）。
  daily 第三槍台灣 05:30，近幾天都準時落在 05:4x，預期 ~05:50 發佈、~05:55 tw-hold 重算。
  daily 被取消不接，**daily 失敗（例如稽核步驟紅燈）照樣接**（資料包本身是好的）。
- 備援 cron：原 UTC 22:00 保留，另加 UTC 23:00、00:30。
- 新增 `scripts/bundle_gate.py`（新鮮度閘門）：更新 store 之後比對本機
  `prices_adj`／`chips` 最新日 vs Release `data-latest/_meta.json` 已發佈的 `max_date`，
  **任一個比較新才發佈**，否則後面五步（估值/打包/發佈/觸發 tw-hold/commit）全部跳過。
  取不到 meta 或腳本例外 → 一律發佈（寧可多發不要漏發）。
  `workflow_dispatch` 手動觸發**不過閘門**（救援用）。
- 端到端驗證（本輪做過）：手動跑 daily → `workflow_run` 自動觸發 publish →
  閘門判「沒有比已發佈的新」→ 五步 skipped、run success、**沒有多餘的 tw-hold 重算**。
  **還沒在真實環境驗到的是「有新資料 → 閘門放行 → 完整發佈」那一側**（只有單元測試）。
