⚠️ **不要為了讓數字好看而反覆調參數。** 這是可行性檢查不是最佳化——
**這條線本來就不宣稱報酬**，調參數調不出報酬，只會調出過度擬合的錯覺。

## 3. 實驗 B · 價值/定存值不值得做（tw-hold，~1–2 session）

**這個實驗值 300 萬，而且它可能會說「不要做」。**

### B-0 · 要回答的問題

> 如果從 **2015 年**就照 `tw-hold/PRD.md` §6（價值）與 §7（定存）的規則**季換股**，
> 這 10 年的結果是什麼？

**必須產出的數字（每條線各一組）**：

| 指標 | 為什麼要 |
| :--- | :--- |
| 🔴 **每期候選檔數**（先算這個！） | **可行性**。定存線疊了「殖利率 ≥ 5%」+ 連配 5 年無減配 + FCF 覆蓋 + 填息率 ≥ 60% + 近 3 年含息報酬 ≥ 0 + 負債比 ≤ 0.75 + 近 4 季 EPS 為正。台股大盤殖利率才 3–4%，這一疊下來**某些季度可能只剩 3–5 檔，組合根本建不起來**。如果是這樣，後面的報酬數字沒有意義——先回報使用者調門檻 |
| **含息年化報酬** | 🔴 定存線要對標「使用者賣掉的美國特別股/債券 ETF 的稅後殖利率」。對標不到，整個轉換就不該做 |
| **最大回撤** | 🔴 這筆錢從債券換過來，心理預期是穩定收息。第一年 −20% 會讓他後悔 |
| **平均填息率** | §7.1 的硬門檻是否真的篩掉了「賺息賠價差」 |
| **年換手率** | 季換股的成本。換手太高，交易成本會吃掉價值 |

**對照組（一定要一起跑，否則數字沒有意義）**：
0050 含息、0056 含息、00713 含息（能取到的話）、以及「符合硬門檻但不排序、等權全買」
——最後這組是在檢查**排序有沒有貢獻**，還是光靠硬門檻就夠了。

### B-1 · 資料與陷阱

- 資料：`tw-swing/data/fundamentals/*.parquet`（514 檔、2015Q1–2026Q2，已版控）
  + 本地 PER + 股利 + 日線 + §1.2 補的三樣。
- 🔴 **公告日遞延一定要套**：財報用 `period_end + 45 天`（`twswing.value.loader` 的
  `STATEMENT_LAG_DAYS`），月營收用 `available_date`（+9 天）。
  **沒套 = 未來函數 = 整個回溯作廢，而且結果會好得不像話。**
- 🔴 **生存者偏差**：`data/fundamentals/` 是**用今天的前 500 大**抓的。
  用它回溯 2015 年，等於已經知道誰活到今天。
  → **這個偏差沒辦法完全消掉**（免費層拿不到歷史成分股），
  **所以報告裡必須明白寫出來，並把結論當上界看待**。不要假裝它不存在。
- 交易成本：照 tw-swing 的口徑 **0.585%**（來回）。
- 🔴 **定存線的殖利率門檻用「使用者裁決值」，不是 PRD v1.0 那個 4%**：
  **目標 5.5%、硬底線 5%**（2026-09-07 裁決，理由見 `PRD.md` §7.0/§7.3）。
  → 回溯時 `買入殖利率門檻 = max(該股近 5 年平均殖利率, 5.0%)`。
  → **同時跑一組 4% 的對照**，讓使用者看得到門檻拉高的代價（候選變少多少、
    報酬與回撤差多少）。
- 換股日：季中（3/6/9/12），對齊財報公告後（Q1 5/15、Q2 8/14、Q3 11/14、Q4 3/31）。

### B-2 · 怎麼跑

- **不要用 tw-swing 的 `backtest/engine.py`**——那是事件式訊號 + 停損的引擎，
  跟「季換股組合」是不同的東西，硬套會得到沒有意義的數字。
- 寫一支獨立的簡單回溯腳本放 `tw-hold/research/backtest_rebalance.py`：
  ```
  for 每個換股日:
      套硬門檻剔除 → 算因子 rank → 取前 N → 等權
      持有到下一個換股日，記錄含息報酬（用還原序列）
  ```
- 因子邏輯直接用 `tw-swing/src/twswing/value/{factors,screen}.py`（M0 要搬走的那兩支，
  這裡先 import 或複製都行，**這是研究腳本不是產品碼**）。
- **N 取 10 與 20 各跑一次**（清單長度未定案）。

### B-3 · 產出

- 報告 `tw-hold/docs/reports/rebalance_backtest_<日期>.md`：四個數字 × 兩條線 ×
  兩種 N × 對照組，加一段「生存者偏差有多大、結論該打幾折」。
- 在 `tw-hold/docs/PLAN.md` 的 M-1 打勾並填數字。
- ⚠️ **只跑基準版，不要調參數湊過門檻。** 基準版不好看就照實回報——
  那個結論本身就值 300 萬。

## 5. 這些實驗會不會打架（查過了，只有一處要小心）

### 5.1 資料層：**不衝突**（用的是不同資料集）

| | 讀什麼 | 寫什麼 |
| :--- | :--- | :--- |
| **實驗 A** | `data/finmind/revenue/`、`data/finmind/per/`（逐檔 parquet）、`data/store/`（日線） | 只寫報告，**不動任何資料** |
| **實驗 B** | `data/fundamentals/*.parquet`（財報四表）、per、股利、日線 | F1 重抓 → `data/fundamentals/balance.parquet`；F3 新增未還原價 |

- 實驗 A 的 `revenue_accel` / `pe_percentile` 來自 **`data/finmind/`**
  （`twswing.data.fundamentals`），**不是** `data/fundamentals/`（那是 `value.loader` 用的）。
- 所以 **F1 重抓 balance 不會影響實驗 A 的可重現性**。F3 是全新檔案，更不影響。

### 5.2 git 層：**會衝突**——同一時間只讓一個 session 動 tw-swing

實驗 B 的地基補齊（F1）**要改 tw-swing repo 的 `scripts/fetch_fundamentals.py`**，
而實驗 A 也要在 tw-swing 寫報告、改 `RULE_LEDGER.md` / `STATUS.md`。

> 🔴 **規則：一個 session 做一個實驗，做完 commit 再開下一個。**
> 不要開兩個對話並行——它們會改到同一個 repo 的不同檔案，
> 合併時很難看出誰對誰錯。

### 5.3 FinMind 額度：**要錯開**

- 實驗 B 的地基補齊 ~1000 requests（`RATE_CEILING = 500`/hr → 約兩小時）。
- `fundamentals.yml` 排在 **UTC 週六 02:00 = 台灣週六 10:00**。**避開那個時段。**
- 實驗 A **完全不需要新抓取**，所以它跟任何排程都不會撞。

### 5.4 為什麼是 A 先 B 後（不是硬相依，是划算）

1. **A 便宜**（~1 session，零地基補齊），**B 貴**（要先補三樣地基 + 寫回溯腳本）。
2. **A 的證據基礎好**（Y4/Y1 已經有 BENCH 數字，只是換出場），
   **B 是從零驗證**（可能得到「不要做」）。
3. **A 的結論不影響 B，B 的結論也不影響 A**——兩條線是獨立的錢。
   所以順序純粹是「先拿便宜的答案」。

### 5.5 🔴 開工前先 commit

寫這份文件的當下，**tw-swing 與 tw-hold 兩邊都有大量未 commit 的文件改動**
（PRD v3.0、STATUS 改寫、本檔新增…）。
**接手的第一件事是把它們 commit 掉**，否則實驗做完的產出會跟這些混在一起，
分不出哪些是討論結果、哪些是實驗結果。
