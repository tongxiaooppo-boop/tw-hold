## 2. 分類避坑清單

格式：**坑名**｜現象｜成因｜判準／避法｜出處｜對我們的影響。優先級 P0＞P1＞P2。

### A　抓取端

**A1 [P0] 帶日期的請求，回應不自述日期就不可信（靜默失敗全長成 `stat:OK`）**
- 現象：參數格式錯、該用 POST 卻用 GET、查詢越界、換了端點家族 → 200＋「成功」，卻回今天／最新一期／一頁「查無資料」的 4,449 bytes 頁面（32 個年份全部「命中」）；被 CDN 擋回 HTML（TWSE HTTP 428）會被只 try/catch JSON 的程式看成「解析失敗」。
- 成因：官方端點對未知／無效參數的處理是「忽略並回預設」，且不報錯；`stat`、列數、bytes 都不是判準。
- 判準：**請求帶了日期就斷言回應頂層／每列的日期等於請求日；請求帶了期別就斷言回應的期別**；「有回列」「檔案夠大」「stat OK」一律不當證據。同一個標的送兩個不同期別、比對回傳內容是唯一可靠的驗法（「請求的 blob／URL 不同」不算）。
- 出處：CLAUDE L35-66；NE L110-130；DS §21 L511-568；OURS TTP L16-23。
- 對我們：**這是最值錢的一條，selfhost 已做**（對照表 A1）。
- 附：此坑的反例也要記——TSD 曾把 MOPS `t164sb03` 的「year／season 四種組合回應相同」誤判成「參數無效」，2026-09-23 被推翻（真正沒被控制的是 `dataType`：送 `"1"` 一律回最新季且不報錯；`year` 要民國年）。被推翻的是「例子」，不是判準（CLAUDE L46-64）。

**A2 [P0] 端點名字不是證據（`history` 只有今年）**
- 現象：TPEx `tpex_spendi_history`（「上櫃歷史暫停／恢復交易」）362 列，`Date` 欄相異值只有 1 種（民國 115＝2026）；181 檔裡混著權證。
- 成因：命名誤導；頂層是陣列、沒有 `stat/total/notes` 可問。
- 判準：陣列型回應一律印**每個鍵的相異值分佈**；相異值只有一種的鍵當場就講出涵蓋期間。
- 出處：CLAUDE L69-84。對我們：新端點流程應包含此步（目前 ❌，見 A12）。

**A3 [P1] TPEx 舊版／openapi 端點的 `date` 被忽略；真歷史是 `dailyQuotes`**
- 現象：`tpex_mainboard_daily_close_quotes`（`d=` 任意日）、舊版 `stk_quote_result.php` 永遠回「查詢當下的最新日」。
- 判準：改用 `www/zh-tw/afterTrading/dailyQuotes?date=…`，並斷言回應日期（2026-09-15 我們自己也重測過）。民國年要三位補零（`098/06/01` 有效、`98/06/01` 會回今天）。
- 出處：DS §21 L511-568；PLAN L400-406；RC L2266-2273；OURS TTP L25-64。
- 對我們：已避開（對照表 A3）。

**A4 [P1] 同族不同端點，參數行為各不相同**
- 現象：`bulletin/` 家族的 `exDailyQ` 無斜線 GET 靜默回今天，`revivt`／`pvChgRslt` 則回 `stat:參數錯誤`（大聲失敗）；`TWTAWU`、`violation/stop` 的 `date=` 被官方換掉（`params` 回顯自己承認）；`TWT48U` 是預告表沒有歷史。
- 判準：每支端點自己實測；`params` 有回顯就看它有沒有被換掉；沒有 `params` 就看日期／期別回顯；沒有 `total` 就用「大區間切小區間各取一次再加總，差 0」才說沒截斷（`TWT49U` 九年 9,483 筆＝逐年加總 9,483）。
- 出處：NE L96-106、L146-153；RC L1059-1066；CA L128-133。對我們：selfhost 的事件抓取用月／年切段（已間接符合）。

**A5 [P1] 查詢端的 CDN 快取：404 被快取、`?query` 破不掉**
- 現象：`raw.githubusercontent.com` 對檔案連三次 404（其實存在）；未知 query 參數被忽略，`?r=亂數` 無效；WebFetch 讀大 JSON 會被截斷且「被憑空補齊」。
- 判準：改用 `refs/heads/main/...` 路徑；大檔讀 CSV。
- 出處：RC L362-373。對我們：目前走 GitHub Release／API 下載，無此路徑（grep 無 `raw.githubusercontent`）。

**A6 [P1] TLS：TPEx 憑證鏈缺中繼憑證，瀏覽器會替它遮掩，但關驗證不是修法**
- 現象：TWSE 對方送 3 張憑證、TPEx 只送 1 張（`Verify return code: 21`）；系統 CA 與 `certifi` 兩份都驗不過（TSD 2026-09-13 實測）；瀏覽器靠 AIA chasing 補中繼憑證所以「瀏覽器打得開」。另一份紀錄：Python 3.14 的 OpenSSL 對 TPEx 回 `Missing Subject Key Identifier`，以 `OP_LEGACY_SERVER_CONNECT` 解、並實測仍保持 `CERT_REQUIRED`＋`check_hostname`。
- 判準：補鏈是**追加**驗證用的路（照抄「現在是通的站」送的整組），不是關驗證；錯誤訊息不可砍尾巴（可行動的資訊在後半）；自測盯 `verify_mode`、`check_hostname`、原始碼沒有 `CERT_NONE`。
- 出處：CLAUDE L1549-1617；PLAN L5825-5843；MCP spec（櫃買封鎖雲端出口，見 A8）。
- 對我們：**文件之間有衝突**（見 2.H）。tw-swing `watchlist.fetch_json` 會降級成 `verify=False`（記 `tls_verified`）；selfhost 假設 `requests`＋certifi 可驗 TPEx，**我沒在 Actions 上驗證過**。

**A7 [P1] 限流／額度：超額不是變慢，是整窗全部 402；被擋要等整窗過去**
- 現象：FinMind 免費 600 次／小時，超額後每個請求都回 402，3 次重試＋短 backoff 救不了；大量回補後 IP 暫時 403（`ip banned`，`retry_after`）；TWSE 約 3 次／5 秒、TPEx 同；FinMind 的 `TaiwanStockNews` 單次只回一天。逾時環境只殺「這一次呼叫」、背景迴圈還在跑，共用全域游標會讓同一 id 被處理兩次（量測假象，不是資料重複）。
- 判準：自己做滑動視窗節流（略低於官方上限）；402 要等整窗；游標綁在這一輪；留一個「只會等於不會超過」的檢核數。
- 出處：PLAN L643-659；FM L58-60；SF L117-122；NE L165-178；DBM tasks\reports\backfill-2021-report.md L5-20。
- 對我們：selfhost 已有（對照表 A7）。

**A8 [P1] 「被擋」要先分清楚誰擋誰：容器 403 是我方閘道擋；雲端出口被對方擋**
- 現象：開發容器對交易所一律 403（`gateway answered 403 to CONNECT`）＝我方閘道擋、Actions 上是通的；反過來 TPEx 會封 Cloudflare Workers／非台灣機房出口（同一端點從 HiNet 回 200）。
- 判準：在哪個環境得到的失敗，就只對那個環境成立；不要把本機／沙盒的失敗寫成事實。把「回了 HTML」直接讀成「被擋」是多走一步（HO L226-239：真正成因是 body 少了 `subsidiaryCompanyId`）。
- 出處：CLAUDE L1530-1547；MCP spec L114-118、README L177-181；HO L226-239。對我們：INCIDENTS 2026-09-29 就是在沙盒裡無法確認休市而寫成「待人查」。

**A9 [P1] 編碼與解碼：`big5` ≠ `cp950`；`resp.json()` 在 T86 會亂碼；檔案編碼同站不同**
- 現象：ISIN 清單用 `big5` 會把「碁」靜默換成 U+FFFD（13 檔），要 `cp950`；T86 宣告 UTF-8 但 `resp.json()` 亂碼，要 `json.loads(content.decode("utf-8"))`；櫃買匯出的面額變更是 Big5、減資是 cp950（「不要假設同站同編碼」）；ZIP 內檔名 Big5 被當 cp437 解。
- 出處：DS L10-14、L171-175、L640-642；TSD sources README L70-72。對我們：收集端只吃 JSON；ISIN 路徑在 tw-swing 的 TTP 已記。

**A10 [P1] HTML 頁面抓取的三種靜默漏列／截斷**
- 現象：①regex 用 `\s*` 與 `[^<]*` 有歧義，44 萬字單行 HTML 災難性回溯卡死；②「備註」欄的 `<td align=…>` 有文字時是 `left`，只比 `center` 會漏 233 筆（含 2330）卻不報錯；③HTTP 200 但 body 是 0 bytes（TWSE 2025-10 月營收頁）或被截斷缺 `</html>`（TPEx 2022-02 `_0`）。
- 判準：拿已知標的（2330）核對；以結尾／列完整性檢查拒收殘缺頁；官方 HTML 內的「另存 CSV」表單可補（POST `FileDownLoad`）。
- 出處：DS L318-349；DBM revenue-official-source-audit L159、L188-190。對我們：selfhost 不抓 HTML；tw-swing 營收走 OpenAPI。

**A11 [P1] 官方當日資料收盤後會被更正／晚間二次更新**
- 現象：2026-10-05 投信 14 檔、成交量 17 檔在首次收進後被官方更正（例：9929 成交量 21,600→1,771,600）；`TWT93U` 每晚約 20:30 與 22:30 更新，兩次之間取到的是不完整版本且看起來正常；`MI_MARGN` 在收盤後好幾小時才發，19:00 那一發固定回「沒有符合條件的資料」。
- 成因：首次公布時資料未完整（GPT 說「T86 不含更正」與實測矛盾，見 3.20）。
- 判準：近 N 個日曆日每次重抓覆蓋；排程避開更新區間；「更正會延後多久」要自己統計（TSD `_changes.log` 僅 2026-08 起 51 行）。
- 出處：RC L2021-2023；CLAUDE L1118-1119；OURS data-qu §3-2、§6.2。對我們：已修（A11），**3 天窗口夠不夠仍未解**。

### C　還原價與公司行為

**C1 [P0] 還原因子是連乘：一筆假資料的半徑是整條序列**
- 現象：官方上櫃減資表把 `1070925` 打成 `1090925`（6109 亞元，6 個數字逐位相同）→ 該列之前每一列 `cum_factor` 多乘一次，而檔案看起來完全正常；`TWTAUU` 同（代號,日期）重複（3536 於 2015-03-20 三次）不去重會把 2.0258 連乘成 8.32、該檔之前 K 棒灌大四倍且不報錯。
- 判準：**停止買賣型事件一定有停牌缺口**（①我方事件日前最後一筆收盤＝事件日前一交易日→沒有缺口；②且官方「停止買賣前收盤」對不上我方→兩條同時成立才判不成立；只有②是我方價格問題，要報給人看）；是**算出來**的判準、不是黑名單；重複列用「因子是否相同」去重，不是「同日只能一筆」；閘門要擋在進入連乘之前。
- 出處：CLAUDE L86-126；RC L2432-2437；TSD sources README L80-90。
- 對我們：**我方驗證**——`corp_actions` 目前沒有 6109 的假列；3536、3312 的重複／衝突被 `conflict` 旗標記下（`adjust_log.csv` 2 筆）；但**沒有停牌缺口閘門**（對照表 C1）。

**C2 [P0] `cum_factor` 的語意與「未來事件」不變量**
- 現象：因子適用於「事件日**之前**」的列（事件日當天已是新價格、再乘就重複）；最新價 F=1、現價不動；減資表是事前公告表（2026-09-06 就公告到 09-29），**收進一筆還沒發生的減資，今天 1563 的收盤 66.00 會被還原成 84.66，跟看盤軟體對不起來**且不報錯；基準是「資料到哪一天」，不是系統時鐘（容器時鐘曾差過一天）；TSD 的 `adjust.py` 因此另有閘門，擋掉日期晚於交易日曆最後一天的事件。
- 因子不一定 ≤1：減資恆 >1（3536 誠創 f=2.026，九成減資近 10）；認購價高於市價的現增可 >1（3312 f=1.0017）；「應該 ≤1」的過濾會把減資整批丟掉。
- 判準：`F(d)＝所有事件日嚴格大於 d 的因子連乘`；事件日 > 日曆最後一天的一律不寫、不套。
- 出處：RC L465-489、L2439-2450；CLAUDE L1021-1043（基準要用資料最後一天，不是 today）。
- 對我們：❌ **我方驗證：`corp_actions.parquet` 目前有 4 筆日期晚於實價最後日（2026-10-05）的減資（2323、3085、4527、5301，事件日 2026-10-07／10-12）已被 `selfhost_adjust` 套用**；這 4 檔停止買賣中，其 `adj_prices` 最後一列 close 與 `raw_close` 不同（例：3085 14.688 vs 11.40）。目前 `adj_prices` 沒有下游消費者（grep 驗過），所以尚未傷到頁面，但切成主來源前必須修。

**C3 [P0] 現金增資的兩個參考價（A／B）與兩個 repo 的相反結論**
- 官方公式：A＝除權息參考價＝（前收−息值＋認購價×現增配股率）／（1＋無償配股率＋現增配股率）；B＝減除股利參考價＝（前收−息值）／（1＋無償配股率）。**開盤競價基準與漲停基準用 B**（2353 宏碁 2015-01-05：漲停 22.80＝⌊21.35×1.07⌋ 用 B、跌停用 A）。95.5% 的事件 A＝B，隨便抽一天比不出口徑。
- 現象：用 A 當還原因子，現增事件日的還原報酬系統性偏高（TSD 量 463 筆：還原後平均 +0.88%／原始 −1.52%，差約 2.4 個百分點，方向一律偏高）；Yahoo 對純現增事件的階梯約為官方 A 偏離量的 0.78–0.81 倍，**「Yahoo 把現增當不存在（＝B）」被推翻**，無單一公式解釋。

### G　工程慣例

**G1 [P0] 累積型的檔不可整份覆蓋；「這一趟只知道自己那一部分」的寫入一律是合併**
- 現象：分支上的 `data/` 比 main 舊，整檔搬過去就把五分鐘前的一列刪掉（`git diff` 一加一減像「重算過」）；續跑台帳在不帶 `--resume` 時被洗成一列表頭（1,996 列→1 列）；同步程式的步驟蓋掉別條線累積的 `runlog.md`；「還原時從工作區 HEAD 取」會砍掉 main 上的 533 行；合併後列數不得少於 main。
