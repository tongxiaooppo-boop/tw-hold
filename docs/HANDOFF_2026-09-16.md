## 2. 這一輪做了什麼（`607cc06`）

起點是使用者問「0050 卡片為什麼是舊資料」，上一輪（`6a5e0e7`）已經把 0050 從
「拖整包 89MB bundle」改成「讀 tw-swing 本來就有附的小檔」+ CI 端驗證後才落地。
本輪是**審核那一輪 + 修掉審出來的洞**。

### 審出來的三個真問題

1. **`index_006201.parquet` 裡本來就有壞資料**（實測，不是理論風險）：
   2016-08-24、2017-04-10 兩筆 `close = 0`，日報酬序列因此出現 `inf`。
   今天畫面沒壞只因為 `market_status.market_card()` 只吃尾端 200 筆。
   而 `fetch_index_proxy.py` 是「抓到就整份覆寫」，零驗證。
2. **舊的三道驗證全部只看「最後一筆」，防不住整份檔案縮水**。上游若寫出只剩
   最近 30 列的檔：欄位對、sha256 對、最後日期是今天、最後一筆漲跌正常 →
   三道全過 → 覆寫後 `ma_verdict` 因 `len < 200` 靜默回 `None` → 卡片變空白，
   而 `freshness_check` 也抓不到（它只看最後一筆日期，那是新的）。
   **這是整輪唯一「壞了沒人知道」的路徑。**
3. `if prev_close and abs(...)` 讓漲跌幅檢查在 `prev_close == 0` 時整道被短路——
   本意防 ZeroDivisionError，副作用是最嚴重的壞資料反而豁免。

### 改法：`reference/price_series_guard.py`（新，0050／006201 共用）

**兩段式，這個順序是設計重點，別改**：

- **`sanitize()` — 清，不是拒絕**：丟掉 `close <= 0` / `NaN` / 重複日期。
  FinMind **每次全量重抓都會再吐一次同樣的 0**，若設計成「看到就拒絕」，
  006201 會從此天天拒絕、資料凍死。清得掉的東西不能拿來當拒絕理由。
- **`validate()` — 這些才拒絕**（拒絕＝保留舊檔不覆寫、exit 1）：
  - 筆數 `< 250`（餵不動 MA200）或比舊檔縮水 `> 5` 筆 ← 補上洞 2
  - 最後日期比已發佈的舊檔還舊
  - 最後一筆單日漲跌 `> 12%`
  - 重疊區最近 60 天的**日報酬**對不起來 `>= 2` 天（歷史被回填／改寫）

**兩個容易被後人「順手改掉」的設計，先講清楚為什麼**：

- **門檻 12% 不是隨手填的**：實測 2015 年起 2847 筆 0050 日報酬，最大絕對值
  **恰好 10.0%**（台股 ±10% 漲跌停，ETF 同受限），99.9 分位 9.26%。合法值進不了
  10~12% 這個帶。（上一版的 15% 才是憑感覺定的。）
- **重疊區比「日報酬」不比「價格」**：這兩支都是**還原型**序列，每逢除息／分割
  會把事件日之前的價格整段乘上一個常數——**價格會全變、但日報酬只有事件日
  當天那一筆會變**。所以容許 1 天不一致（＝一次合法的還原基準變更），
  ≥2 天才判定歷史被竄改。若有人改成比價格，會天天誤拒。

## 3. 刻意沒做 / 已知限制

- **連假誤報沒解**：`SLACK_DAYS = 2` 蓋不住農曆春節（9~10 天），那段期間每個
  平日開盤前都會告警。評估過「升級式告警（連續 N 天才發）」，要存 stale 計數，
  **為一個告警功能加狀態不划算**；接外部行事曆 API 則是為告警路徑加新的外部依賴。
  折衷：告警訊息裡直接寫明「若正值連假這是已知假警報」。使用者若哪天嫌吵再說。
- **`index_0050.parquet` 沒套 `adjust_per_share`**：`_bundle_close("0050")`（備援
  路徑）走 `bundle_data.prices()` 會套分割還原，`index_proxy.load_0050()` 是純讀檔
  **不套**——兩條路徑理論上可能口徑不一致。**實測目前完全相同**（798 個重疊
  交易日最大相對差 0.0），因為 0050 不在 `SPLITS` 表裡（上游已還原）。
  這是一顆「0050 再分割一次、且上游沒還原時才響」的雷，記在這裡。
- 上一輪已定案不重審的：badge-only 不擋頁、選股規則/因子/verdict 沒碰。

## 4. 踩坑（本輪新增，會再遇到）

**Streamlit Cloud 部署後噴 `AttributeError: 模組沒有某函式`，不是程式 bug。**

本輪真的遇到：雲端說 `reference.index_proxy` 沒有 `load_0050`，但那支函式明明
已經 push。原因是 **Cloud 的主腳本每次 rerun 都重新執行（＝新版），但
`sys.modules` 裡已經 import 過的子模組沿用舊進程的舊物件**。辨識特徵：
**traceback 行號對應新版 `streamlit_app.py`、卻抱怨舊版模組缺屬性**——這組矛盾。

→ 處理：叫使用者 **Manage app → Reboot app**，不要改碼、不要去查 push 狀態/
模組遮蔽/`.pyc`。凡是「在既有模組裡新增函式」的部署都可能再遇到。
