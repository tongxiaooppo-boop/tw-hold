## 0. 時程與運作原則（2026-10-03 使用者定）

| 階段 | 時間 | 內容 |
| :-- | :-- | :-- |
| **現在** | 至 10-04（週末） | **繼續 100% 依賴現有上游**，不動任何現行管線 |
| **測試期** | 從**下週（10-05 起）**開始自建與測試 | 先做 P1 影子收集＋種子封存（§3），再做 P2 還原引擎；自建結果**只落自己的檔、不進現行 bundle、不影響清單** |
| **驗證期** | 測試期之後「一段時間」（以 §3 P3 的對帳達標為準，預設連續 20 個交易日） | 自建與上游並行；沒問題才算「可上線」 |
| **上線** | 驗證期通過後（使用者再拍板） | 自建取得「上游失效時接手」的資格（§P4）；**上游仍是主來源** |
| **之後** | 永久 | **每週與原上游比對**（見下），即使上線後也不停 |

**每週比對（依我的建議、使用者同意）**：
- 不是「驗證完就不管」。上線前後都持續比對，因為官方端點改版、還原價邏輯漏案例（新分割／減資）都是**緩慢漂移**，只靠一次性驗證抓不到。
- 做法：每日並行產出對帳摘要（`data/derived/selfhost_recon.json`，P3），**每週（建議週六）另跑一個彙總 workflow**，把當週每日對帳結果壓成 `selfhost_recon_weekly.json`：
  當週自建 vs 上游的檔數差、還原收盤差 > 0.5% 的檔清單（逐檔列、標原因：分割／減資／口徑）、法人／融資券數字差、不可補回缺漏天數。
- **紅線（任一成立 → 該週標「不可接手」並在交接單／心跳露出）**：還原收盤差 > 0.5% 的檔數超過 1%；任一天上櫃檔數 < 上游 98%；法人或融資券總量差 > 1%。
- 週報只攤事實、不自動切換來源（切換永遠是人拍板）。放 tw-hold（公開 repo，不吃額度）。

## 1. 目標與跟現有上游的關係

| | 角色 |
| :-- | :-- |
| 現有上游（maosof007 `data_pack.zip`） | **種子（歷史）＋每日對帳基準＋失效時的接手對象**，不是永久依賴 |
| tw-hold 自建上游 | 長期目標：自己用官方來源產出同 schema 的 `prices_adj`／`chips`／`margin`，**和上游並行跑、每天對帳**，驗證過才有資格接手 |

**要產出的東西（跟 bundle 同 schema，下游不用改）**：還原日線（OHLCV＋成交值）、法人買賣超（外資／投信／自營）、融資券。
**不碰**：財報（已走 FinMind，已 commit）、估值快照（已自抓）、總經（已自抓）。

> 判斷：與其做「鏡像上游」，不如把上游當**種子與裁判**。種子只在初始化用一次（取得 2015→今的歷史），之後自己每天往後長；裁判用來驗證我們的還原價算得對不對。這也避開「公開轉載別人 220MB 資料包」的問題。

## 2. 為什麼不能等到上游死掉才開始（關鍵限制）

- **TPEx 官方每日行情端點只回最新一天、`d` 參數被靜默忽略**（`tw-swing/docs/reference/twse_tpex_pitfalls.md` #1，2026-09-15 實測）。
  → **上櫃日線一天沒抓就補不回來**（只能找替代來源）。所以**每日原始資料的「影子收集」必須盡早開始**，比還原引擎更急。
- 還原價最難（官方給未還原價；直接接在還原序列後面，每次除權息產生假跳空，污染 MA／RSI／ret 全部指標）。這要時間驗證，不能臨時趕。
- 上游死掉的偵測條件已存在：資料包 `Last-Modified` > 30 小時（`update_data.py --require-fresh`）。

## 3. 分期

### P0 — 決定與保底（小）
- **種子歷史封存**（§6-1 已決定放 tw-swing 私有 Release，每週一次、留最近 4 份）。這是最低成本的保底，可與 P1 並行先做。
- 不依賴這步也可先做 P1。

### P1 — 影子收集（**最優先、成本低、不可延後**）
每個交易日盤後，tw-hold 的 Actions 抓官方「當日原始」並 **append 進 repo**（小檔、每日一檔或單一 parquet 累加）：
| 資料 | 官方來源（**待逐一實測，標 ✅ 才算數**） | 備註 |
| :-- | :-- | :-- |
| 上市日線（未還原 OHLCV、成交值） | TWSE `STOCK_DAY_ALL`／`MI_INDEX`（帶日期？待驗） | `snapshot_pcf` 已用過 `STOCK_DAY_ALL`（抓收盤價） |
| 上櫃日線 | TPEx openapi `tpex_mainboard_daily_close_quotes`（**僅最新一天**） | 一天不抓就永久缺 |
| 法人買賣超（個股） | TWSE `T86`（帶日期？待驗）；TPEx `tpex_3insti_daily_trading`（實測有 `Date` 欄、似為最新日） | 單位／欄位要對齊 data_pack |
| 融資融券（個股） | TWSE `MI_MARGN`；TPEx 融資融券 openapi | 同上 |
- **規則**：請求帶日期就**斷言回應日期等於要的那天**（pitfalls 檔頭「最重要的一條習慣」），否則丟棄並告警。
- 掛在新 workflow（建議 `selfhost_collect.yml`，台北盤後約 16:30 與 18:30 各一次，沿用 `chip_flow_evening` 的 commit／重試模式與 concurrency group）。tw-hold 公開 repo，**不吃額度**。
- 驗收：連續 10 個交易日，上市＋上櫃檔數 ≥ 當日 data_pack 檔數的 98%。

### P2 — 還原引擎＋對帳（最難）
- 還原因子：現金股利／股票股利／分割／減資。資料來源：已在 bundle 的 `dividend.parquet`（FinMind）＋ `reference/corporate_actions.py`（手動 SPLITS）＋ TWSE 除權息結果表（參考價，待驗）。
- 向後還原：除權息日以前的價格乘因子；因子＝參考價／前一日收盤（優先用官方參考價，現金股利公式為備援）。
- **驗證方式（本計畫的核心優勢）**：data_pack 的還原序列是現成的標準答案。對**重疊區間**逐檔比對自算還原收盤：
  驗收＝最近 250 個交易日、≥ 99% 的檔數 |差| < 0.5%；剩下的逐檔列清單人工看（多半是分割／減資邊緣案例）。
- 自己的還原結果**不覆蓋**上游，另存 `selfhost_prices_adj.parquet`。

### P3 — 並行跑＋每日對帳報告（＋每週彙總，見 §0）
- 每天產出對帳摘要（檔數差、還原價差 > 閾值的檔、法人／融資券數字差），寫進 `data/derived/selfhost_recon.json`，頁面不顯示、只給心跳／人看。
- 連續 20 個交易日達標才進 P4。

### P4 — 接手機制（失效時救援）
- **偵測**：上游 `Last-Modified` > 30h，或對帳連續 3 天上游缺檔。
- **切換**：tw-hold 的 `rebuild.yml` 在 bundle 過期時，改用 `selfhost_*` 檔組成等價 bundle（同 schema、同 G1 檢查），清單照出；tw-hold 端自癒、不需要 tw-swing。
- **tw-swing 側**（私有 repo，吃額度）：需要一個 `import_selfhost.py`，把自建檔轉成 `data/store/` 格式。**這步是否做另議**——tw-swing 規則搜尋已封盤、短線清單才用到日線；若上游死了，先保 tw-hold，tw-swing 之後再決定。
- 寫成救援 runbook 放進 `DATA_FLOW.md` §4.4（取代現在的「只有藍圖」）。

## 4. 風險

| 風險 | 緩解 |
| :-- | :-- |
| 還原價誤差累積 → 均線指標悄悄偏 | P2 對重疊區間量化驗收；自算結果只在接手時才進 bundle，且對帳報告每日產出 |
| TWSE／TPEx 端點改版或限流 | 請求帶日期斷言回應日期；失敗不覆寫、保留舊檔；沿用 pitfalls 清單；節流退避層等真的被擋再寫 |
| 影子收集漏天（尤其上櫃） | 一天兩班（16:30／18:30）；仍漏的天在對帳報告標「不可補回」，不假裝完整 |
| 官方欄位口徑與 data_pack 不同（單位、含不含零股／鉅額） | P2 對帳時逐欄對照；口徑差異寫進 `docs/` |
| 工程量大、容易半途 | 嚴格分期：P1 單獨有價值（至少讓「上櫃不再永久缺」），P2 以後可停 |

## 5. 工程量粗估（工作段，非日曆天）

P1 約 1 段（4 支 collector＋1 個 workflow＋測試）；P2 約 2–3 段（還原引擎＋對帳腳本，最花時間在案例）；P3 約 0.5 段；P4 約 1 段（tw-hold 端），tw-swing 端另算。
**建議順序：P1 → P0（種子）→ P2 → P3 → P4。** P1 一做就開始累積（每多一天就少一個永久缺口）。

## 6.5 附帶：本機同步腳本 `sync_local.py`（使用者 2026-10-03：「跟自建上游一起做，下週」）

起因：`git pull` 帶不回 tw-swing `data/store/`（`.gitignore` 第 3 行，CI 也不 commit 它），本機沒有自動化，要靠手動 `update_data.py`（預設路徑已失效）。設計：
- 位置 `tw-swing/scripts/sync_local.py`（母表屬 tw-swing）。流程：①兩 repo 追蹤檔有改動就**停下並列出**（不 stash、不丟棄）→ ②兩邊 `git pull --ff-only` → ③`update_data.py --skip-watchlist`（**必加**：不加會重抓處置股／月營收當日快照，弄髒 CI 已 commit 的 `data/revenue/`、`data/watchlist/` 當日檔）→ ④`--hold` 時再呼叫 tw-hold `refresh_local.py` → ⑤結尾驗證報告（母表三份、git 追蹤資料、bundle 的最新日；落後標紅）。
- **資料來源做成參數**（`--source upstream|archive|selfhost`）：現在預設現有上游；封存／自建上線後可改指向 tw-swing 私有 Release 的封存檔或自建檔，不再綁死單一來源。順手修 `update_data.py` 失效的 `DEFAULT_PACK`（改可設定）。
- 每週自動：Windows 工作排程器（沿用 `backup/backup.ps1` 做法），週日早上、`StartWhenAvailable`（沒開機則補跑），log 寫 `backup/logs`。**註冊排程器會改使用者機器設定，指令備好後由使用者同意再執行。**
- 限制：每次約 220MB／2 分鐘，只適合每週。
